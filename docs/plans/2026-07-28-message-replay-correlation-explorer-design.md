# Message Replay and Correlation Explorer Design

## Goal

Turn messages visible to BusLane into a safe debugging and test-data workflow. Users can trace related messages across loaded and live-streamed sources, clone and edit one selected message, replay it to a queue or topic, and review or export the local replay audit history.

This design implements GitHub issue #155. Replay is intentionally scoped to one selected message at a time. Replaying an entire correlation group is out of scope.

## User Experience

BusLane adds a Correlation Explorer entry to the navigation sidebar. Opening it displays correlation groups collected during the current application session. The explorer combines messages loaded in the Messages panel with messages observed by Live Stream.

Groups use `CorrelationId` when it is present. Messages without a correlation ID use `SessionId` as a fallback. Messages with neither value are not displayed as correlation groups. Selecting a group shows its messages chronologically, including:

- source type: loaded or live stream;
- namespace and environment;
- current queue, topic, or subscription;
- enqueue time and sequence number;
- message and session identifiers;
- system and application properties;
- body and content type.

Selecting a timeline item exposes a Replay action. Replay opens an editable clone of the selected message and a destination selector for queues and topics in the active namespace.

Before sending, BusLane always displays a preview containing:

- destination namespace, environment, and entity;
- body and metadata;
- application properties;
- fields changed from the source message;
- immediate or scheduled delivery;
- configured rate limit.

Confirmation is mandatory. Production-tagged destinations require an additional explicit acknowledgment of the production warning.

After the attempt, the explorer displays the outcome in replay history. The user can export replay history as JSON.

## Architecture

### Normalized correlation messages

Loaded `MessageInfo` instances and streamed `LiveStreamMessage` instances are normalized into a common immutable `CorrelationMessage` model. The model carries the original message data together with source context that the Azure Service Bus message itself does not provide:

- source kind;
- namespace display name;
- connection environment;
- entity name and type;
- topic and subscription names when applicable;
- observation timestamp.

This prevents explorer grouping and rendering logic from depending on two different source models.

### Session catalog

An `ICorrelationMessageCatalog` service owns messages observed during the current application session. It:

- accepts normalized loaded and streamed messages;
- deduplicates repeated observations of the same message in the same entity;
- caps storage at 2,000 messages and evicts the oldest observations;
- groups first by non-empty `CorrelationId`, then by non-empty `SessionId`;
- returns group messages in chronological order.

The catalog is intentionally in memory. Message bodies collected for correlation exploration are not persisted automatically.

Loaded-message ingestion occurs after successful message-page loads. Live-message ingestion occurs when the live-stream buffer flushes messages to the UI. Both paths supply the active connection and entity context.

### Correlation Explorer

`CorrelationExplorerViewModel` presents catalog groups, the selected chronological timeline, the selected message details, replay history, filtering, and export. `FeaturePanelsViewModel` owns the explorer panel lifecycle in the same way it owns Live Stream, Charts, and Alerts.

A dedicated `CorrelationExplorerView` keeps the feature independent of the existing Messages and Live Stream layouts while allowing both to contribute data.

### Replay request construction

`IMessageReplayService` owns replay validation, preview construction, throttling, scheduling or sending, and audit recording. UI ViewModels do not construct Azure Service Bus calls directly.

A `ReplayRequest` contains:

- source message identity;
- destination entity and entity type;
- body and content type;
- standard Service Bus metadata;
- application properties;
- optional scheduled enqueue time;
- a positive messages-per-second rate limit;
- namespace and environment context used by safety validation.

The editor preserves message metadata and application properties by default. `MessageId` is regenerated by default to avoid duplicate-detection suppression. The user may deliberately enter another message ID, including the original value.

The service generates a `ReplayPreview` with validation errors, warnings, destination context, and a field-level source-versus-request change summary. Sending cannot proceed unless preview validation succeeds and the required confirmation state is present.

### Rate limiting and scheduling

Replay remains single-message. A configurable messages-per-second limit applies across replay attempts so repeated clicks or commands cannot exceed the configured rate. The limiter is local to the application process.

When a schedule time is supplied, the replay service uses the existing `ScheduleMessageAsync` path. Otherwise it uses `SendMessageAsync`.

### Audit history

`IReplayAuditStore` persists a local append-style audit record for every meaningful outcome:

- preview validation failure;
- confirmation cancellation;
- send or schedule attempt;
- success;
- failure.

Records contain timestamps, source identity, destination namespace/environment/entity, schedule information, the rate limit, validation messages, changed-field names, and the send result. They never contain connection strings, Azure tokens, or credentials.

The store follows existing secure local-file patterns through `AppPaths`, `SafeJsonSerializer`, a mutation lock, and secure file creation. Audit export uses the existing file-dialog abstraction and emits formatted JSON.

## Safety Rules

- Destination entity and message body are required.
- Application property keys must be non-empty and unique.
- Rate limit must be positive.
- Scheduled enqueue time must be a valid future timestamp.
- Session-enabled destinations require a session ID.
- The preview and general confirmation are always required.
- Production-tagged connections also require production-warning acknowledgment.
- A replay command cannot bypass validation by invoking the service directly.
- Connection strings and credentials are excluded from models, UI, logs, audit files, and exports.
- Send exceptions are converted into visible replay results and audit entries.

## Error Handling

Catalog ingestion ignores duplicate observations but does not hide invalid source data from the timeline.

Validation failures remain in the editor and are also visible in replay history. Transport or scheduling failures keep the editor open, show the error, and add a failed audit record. Audit persistence failure does not disguise the send outcome; it produces a separate user-visible warning and application log entry.

Cancellation tokens flow through send, schedule, persistence, and export operations. Expected user cancellation does not appear as an application error.

## Testing

Unit tests cover:

- normalization of loaded and streamed messages;
- correlation grouping and chronological ordering;
- session-ID fallback and omission of ungrouped messages;
- deduplication and 2,000-message eviction;
- replay request construction and application-property preservation;
- default message-ID regeneration and deliberate message-ID changes;
- scheduled and immediate replay paths;
- rate limiting across replay attempts;
- destination, property, session, schedule, and rate validation;
- mandatory confirmation and production acknowledgment;
- successful, failed, canceled, and validation-failed audit entries;
- audit persistence and JSON export;
- explorer selection, filtering, replay commands, and panel lifecycle;
- critical XAML bindings and navigation entry.

The existing full `dotnet test` suite remains the final regression check.

## Out of Scope

- Replaying an entire correlation group or batch.
- Persisting captured message bodies between application sessions.
- Correlating messages not visible to the current BusLane process.
- Replaying to a different saved connection or Azure namespace in the first version.
- Server-side distributed rate limiting.
